# TDS Brain App: phase 1 (working MVP)

Date: 2026-11-11 · Size: XL (this doc is phase 1 of 3) · Branch: `phase-1-mvp` · Explainer: `docs/explainer.html`

## Objective

Give the team a simple app "face" for the Agency Brain that runs in Chrome on their own laptop, so nobody
needs a terminal or an IDE to use the brain. Phase 1 proves the whole loop on Ian's laptop: open the app,
pick a skill or type a request, watch Claude answer, answer its questions with buttons, approve or refuse
what it wants to do, and see and tick brain to-dos.

## User decisions (fixed)

- Internal TDS tool. **Claude Code only**; no second engine and no engine-swapping layer.
- **Detached from the brain.** The app lives in `~/My Repos/tds-brain-app`, outside `~/agencybrain`. It keeps
  nothing of the brain's and the brain knows nothing about it. Terminal and IDE stay equal ways in.
- **Local only.** No git remote, nothing published, nothing written into the brain repo by the build.
- Runs in Chrome from a small local server. Lightweight. No Electron.
- Each person uses their own installed, unmodified Claude Code and their own Claude sign-in. The app never
  handles sign-in. (Usage-rules position accepted by Ian.)
- The shell has: a sidebar menu, pinned skills, "used often" skills, a brain to-do list, room for more panels.
- When the brain updates (skills, rules, content), the app must pick it up with no app change.

## Facts already checked (2026-11-11)

- Agent SDK `@anthropic-ai/claude-agent-sdk` 0.3.322, pointed at the installed `claude` 2.1.322 with
  `pathToClaudeCodeExecutable`, `cwd` = the brain: used the subscription sign-in (`apiKeySource: none`),
  fired the brain's 6 session-start hooks, loaded 324 skills and 21 connected MCP servers.
- Streaming input (an async iterable of user messages) keeps one session open across turns. `system:init`
  is emitted again on every turn; one `result` per turn.
- `canUseTool` fires in `permissionMode: 'default'` for `AskUserQuestion` (answers returned in
  `updatedInput.answers`) and for `Write` (a `deny` stopped the write). Its third argument carries `title`,
  `displayName`, `description`, `suggestions`, `toolUseID`, `signal`.
- Node 22.23 runs `.ts` files directly (type stripping), so the server needs no build step.
- Brain conventions: identity = `node tools/whoami.cjs --json`; a to-do is `todo/YYYYMMDD-name.md` with
  frontmatter (`assignee`, `title`, `due`, `project`, `client`); ticking one moves it to `todo/done/`;
  skills are `.claude/skills/<name>/SKILL.md` (frontmatter `description`, `roles`, `maturity`,
  `argument-hint`, `members`, `user-invocable`); commands are `.claude/commands/<name>.md`; clients are
  folders in `clients/` (skip names starting `_`); usage is `z-logs/team-usage/<slug>.jsonl`, with three
  line shapes that count: `{"event":"skill","name":…}`, `{"event":"command","name":"/gm"}` (a typed slash
  command, which is how the app launches skills) and `{"skill":…,"ts":…}` with no event.
- A typed `/name` never calls the Skill tool, so the brain's `skill-role-gate.cjs` hook does not fire for it.
  The app's server must refuse a role-restricted skill itself.
- The SDK's permission `suggestions` can be broad (`Bash(node:*)`, `setMode`, `addDirectories`) and arrive
  with a `localSettings` destination.
- The Agency Brain app auto-commits and pushes any non-ignored change in `~/agencybrain` about 90 seconds
  after it settles. So a direct write to the brain is a publish to the team.

## Decisions

1. **Stack: TypeScript everywhere; Node server run from source; React + Vite client built to static files.**
   Server uses only `node:http` (no Express). Client is React 19, plain CSS with design tokens, `marked` +
   `DOMPurify` for replies. Tests in Vitest, lint in Biome, packages with pnpm.
   Plain: few moving parts, so it starts fast and there is little to break or keep updated.

2. **One process, one port.** `pnpm start` runs `server/index.ts`, which serves the built client and the API on
   `127.0.0.1:3877` and opens Chrome. No separate dev server or proxy.
   Plain: one thing to start, and it is only reachable from this laptop.

3. **The engine is the real Claude Code, started in the brain root.** Every chat is an SDK `query()` with
   streaming input, `cwd` = brain root, `pathToClaudeCodeExecutable` = the installed `claude`,
   `settingSources: ['user','project','local']`, the Claude Code system prompt preset, and
   `includePartialMessages: true`. The model is not set (each person's own default applies).
   Plain: the app gets exactly the brain the terminal gets, including role gates, logging and connectors.

4. **Client context is a short appended instruction, not a different folder.** Choosing a client appends one
   line to the system prompt (`The user is working on the client in clients/<slug>/ …`); `cwd` stays the
   brain root so the brain's rules always load.
   Plain: picking a client points Claude at the right folder without losing any house rules.

5. **Permission mode is `default`, with three answers: Allow, Allow for this chat, Don't.** Requests reach
   the UI through `canUseTool` as plain cards. "Allow for this chat" returns the SDK's own `suggestions`,
   narrowed to session scope only, so nothing is ever written to settings files. No skip-permissions mode
   exists in the app.
   Plain: Claude asks before it changes anything, in words, and a yes never becomes a permanent rule.

6. **Questions are buttons.** `AskUserQuestion` arrives through the same callback and is shown as option
   buttons (multi-select where asked) with a free-text box as the escape hatch.
   Plain: the 37 skills that ask setup questions become click-through forms.

7. **Events are normalised on the server.** The client never sees raw SDK messages. `server/engine/event-map.ts`
   turns them into the small `ChatEvent` set in the contract, numbered per session and kept in memory so a
   page reload replays the chat.
   Plain: reloading the page does not lose the conversation, and SDK changes are absorbed in one file.

8. **The brain is read fresh, watched, and never imported.** `server/brain/*` parses files and runs brain
   tools as child processes (`tools/whoami.cjs`). It never `require`s brain code. A debounced file watch
   sends `brain-changed` to the page, which re-fetches.
   Plain: a skill a scout adds shows up in the app within seconds, with no restart and no app release.

9. **Skills list = brain skills + brain commands, filtered by role.** A skill beats a command of the same
   name. Hidden: skills whose `roles:` excludes the person, and `user-invocable: false`. (`members:` is a
   vendor packaging flag, not a hide signal.) Unknown identity is treated as `team` for hiding. The server
   also refuses a typed `/name` for a restricted skill (`not-allowed`), because the brain's hook does not
   fire for typed commands.
   Plain: team seats do not see owner-only tools; nobody sees internal plumbing.

10. **One direct write to the brain: ticking a to-do.** It moves `todo/<file>` to `todo/done/`, exactly as the
    Workbench does. Ids are validated against the live listing (no paths from the client). Everything else
    that changes the brain goes through Claude with approval.
    Plain: ticking a to-do is instant; anything bigger is done by Claude where you can see and approve it.

11. **App notes live in `data/` inside the app folder** (`data/prefs.json`: pins, last client, panel state),
    git-ignored, written atomically, tolerant of a missing or corrupt file.
    Plain: your pins are yours, stay on your laptop, and can never break the app.

12. **Security model (gate before any team use).** Bind `127.0.0.1` only. Reject any request whose `Host` is
    not `127.0.0.1:<port>` or `localhost:<port>`. A random launch token is exchanged once at `/auth` for an
    `HttpOnly; SameSite=Strict` cookie; every other route needs it (constant-time compare). Requests that
    change anything must carry a matching `Origin` and `Content-Type: application/json`. No CORS headers.
    Strict CSP (`script-src 'self'`), and every reply is sanitised before it is shown. Body size capped.
    Plain: no website you visit, and no other program without your files, can drive Claude through the app.

13. **Brain discovery.** `TDS_BRAIN_PATH`, else `~/agencybrain`. (Phase 1 does not read the Agency Brain
    app's config: it holds a token.) If neither is a brain, the app shows a plain "can't find your brain"
    screen.
    Plain: it finds the brain by itself on a normal install.

14. **Sessions.** Up to 4 live chats. Each keeps its process until closed or 30 minutes idle. Past sessions
    come from Claude Code's own history (`listSessions` for the brain folder) and can be reopened: the app
    shows the earlier messages and resumes with `resume`. A chat started in the app can be continued in the
    terminal and the other way round.
    Plain: chats are Claude Code's, not the app's, so you can switch faces mid-job.

15. **Launching a skill** opens a new chat with `/<name> ` in the message box, showing its description and
    argument hint. The person adds detail (or not) and sends. No per-skill forms in phase 1.
    Plain: every skill works on day one, including ones added later; tuned forms come in phase 2.

16. **Out of scope for phase 1:** output/file preview panel, per-skill forms, installable PWA, file
    drag-and-drop, voice, Windows testing, team packaging and auto-update, adding/editing to-dos.

Overseer decisions on the three open questions: (a) `members:` is not a hide signal; (b) keep 4 chats and
30 minutes, timed only once a turn has finished, and at the cap close the longest-idle chat; (c) pure
`default` mode, no app-side allow list (allow rules belong in the brain's own `settings.json`, where the
terminal benefits too).

## Amendments from the overseer pre-review (binding; they override the text above where they differ)

A1. **"Allow for this chat" is narrowed and labelled.** From the SDK's `suggestions`, keep only `addRules`
    with behaviour `allow`, `addDirectories`, and `setMode: 'acceptEdits'`; drop everything else. Rewrite
    every kept item's `destination` to `'session'`. Honour `suppressAlwaysAllowRule`. Build a plain sentence
    saying exactly what it covers and send it as `sessionAllowLabel`; if nothing is kept, send `null` and the
    button is not shown.
    Plain: "Allow for this chat" always says what it covers, and can never become a permanent rule.

A2. **Rendering and page security.** Response header on every page and API reply:
    `Content-Security-Policy: default-src 'self'; img-src 'self' data:; connect-src 'self'; form-action 'none'; base-uri 'none'; frame-ancestors 'none'`
    (so no inline scripts or styles: the client uses stylesheet files only, no `style=` attributes built
    from data). Also `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. DOMPurify forbids
    `style`, `form`, `input`, `button`, `textarea`, `select`, `iframe`, `object`, `embed` and the `style`
    attribute; links open in a new tab with `rel="noopener noreferrer"`; images are limited to `data:` and
    same-origin by the CSP. Only assistant text is markdown; every other field is plain text.
    Plain: a poisoned web page or email that Claude has read cannot leak your data through a hidden image or
    run code in the app.

A3. **One stream per tab.** `GET /api/stream?session=<id>&after=<seq>` carries app events and the open
    chat's events as `StreamFrame`s. Switching chat reconnects. There are no other event routes.
    Plain: several tabs can be open without one freezing.

A4. **Reopening a past chat.** `POST /api/sessions` with `resume` (and no prompt) creates a live chat in
    `idle`, with `sdkSessionId` set at once, and replays its earlier messages as `user-message` /
    `assistant-message` events (via the SDK's `getSessionMessages`). The engine starts on the first message,
    with `resume`. `resume` must be in `listSessions` for the brain folder and not already live. There is no
    separate history route.
    Plain: opening an old chat shows what was said, and costs nothing until you type.

A5. **Client is fixed per chat.** The appended instruction is recorded on the first turn and ignored on
    resume, so the client cannot change mid-chat. The slug is validated against `clients()`.
    Plain: a chat keeps the client it started with; start a new chat to switch.

A6. **Environment.** The engine's `env` is the server's, minus `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`,
    `CLAUDECODE` and `CLAUDE_CODE_ENTRYPOINT`. If `system:init` reports an `apiKeySource` other than `none`,
    send a warning `notice`.
    Plain: the app can never quietly bill an API key instead of the person's own sign-in.

A7. **Sign-in to the app itself.** Serve on `127.0.0.1` only and refuse `localhost` (cookies do not carry
    between the two). The launch token is created once, kept in `data/runtime.json` (file mode 0600) and
    reused across restarts; the cookie has `Max-Age` of 30 days, so closing Chrome does not lock anyone out.
    Running `pnpm start` while the server is already up just opens Chrome at `/auth?token=…`. A visit
    without the cookie gets a plain page: "Open TDS Brain from its launcher". Cookies ignore ports, so the
    `Origin` check is the real defence against other local apps: test it from another local port.
    Plain: closing the browser never locks you out, and another program on the laptop cannot drive the app.

A8. **Lifecycle.** Close a chat gracefully: end the input stream, wait for the engine to finish (so the
    brain's session-end sync hook completes), then `close()`. Close all chats on SIGINT/SIGTERM. The idle
    timer runs only when a turn has finished, never while a question or approval is waiting. At the cap,
    close the longest-idle chat; if all four are busy, refuse with `too-many-chats`. `turn-end` carries
    `interrupted`.
    Plain: no stray Claude processes are left behind, and a chat never dies while it waits for your answer.

A9. **Helper agents.** Text and tools from a helper agent carry `parentToolUseId` and are shown nested
    under the tool that started them, not as part of the reply. One `messageId` per text block.
    Plain: a helper's working-out does not get mixed into Claude's answer.

A10. **Small honesty points.** Show the chat's `claude --resume <id>` line somewhere discreet (app chats do
    not appear in the terminal's own resume picker). Skills that run as a forked helper (`context: fork`)
    cannot show question buttons; that is an SDK limit, so no special handling.
    Plain: you can always carry a chat on in the terminal.

A11. **Testing must not touch the shared brain (Ian, 2026-11-11: "this MUST NOT touch anything outside my
    personal use").** (i) No builder, test or script may write to `~/agencybrain` or start a Claude session
    there. Every automated test runs against the fake brain in `test/fixtures/brain` (copied to a temp
    folder when a test writes). (ii) The app's one direct write, ticking a to-do, ships switched off:
    `AppPrefs.directWrites` defaults to `false`; the server refuses `POST /api/todos/complete` with
    `not-allowed` and the page shows no tick boxes until the person turns it on in Settings, where the
    wording says plainly that it changes the shared brain. (iii) The lead's end-to-end check uses a
    throwaway fake brain via `TDS_BRAIN_PATH`. A chat in the real brain is for Ian to start himself.
    Plain: building and testing the app cannot change anything the rest of the team sees.

## Amendments from the reviews (binding; 2026-11-11)

A12. **The approval card shows everything it approves.** Nothing is silently shortened. The detail is shown
    in full in a scrolling box. A `Bash` command longer than 20,000 characters is refused automatically
    (Claude is told to split it up) and a notice says so. For any other tool whose detail is over the
    limit, the detail is shortened and `warning` says plainly that not all of it is shown. A file inside
    the brain folder is shown relative to it; a file outside it gets the warning "This file is outside the
    brain folder."
    Plain: a planted instruction cannot hide the dangerous end of a command below the fold.

A13. **"Allow for this chat" says all that it grants.** The sentence has the shape "For the rest of this
    chat, Claude won't ask before …". For the engine's edit mode it reads "creating, changing, moving and
    deleting files in the brain folder", because that mode also lets through `rm`, `mv`, `cp`, `sed`,
    `mkdir` and `touch`. On the card the order is Allow, Don't allow, then a quieter "Allow for this chat".
    Plain: the button that lets Claude delete files says "delete", and it is the quietest of the three.

A14. **Replies cannot dress up as the app.** DOMPurify uses an allow list of attributes (`href`, `title`,
    `alt`, `src`, `start`, `colspan`, `rowspan`); `class`, `id` and everything else are removed.
    Plain: a poisoned reply cannot draw a fake "Needs your approval" box with a button that leaks data.

A15. **The long-lived secret never goes in a web address.** `/auth` takes a single-use code that expires
    after 60 seconds. The server makes one for itself at start. A second `pnpm start` proves it knows the
    secret (an HMAC over a fresh nonce, never the secret itself) at `GET /auth/code` and gets a code back;
    that route refuses any request that looks like it came from a browser. Deleting `data/runtime.json`
    and restarting makes a new secret. This replaces the `/auth?token=…` wording in A7.
    Plain: what ends up in browser history is a used-up code, not a key that works for ever.

A16. **No quiet billing by another route.** The engine's environment also drops `CLAUDE_CODE_USE_BEDROCK`,
    `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`,
    `ANTHROPIC_VERTEX_BASE_URL` and `AWS_BEARER_TOKEN_BEDROCK`.
    Plain: a chat cannot be charged to a company cloud account without anyone noticing.

A17. **Open chats are always in view.** The sidebar lists open chats with their state and a "Waiting for
    you" badge; the "Chat" menu item goes. The page remembers the open chat for the tab (sessionStorage)
    and returns to it on reload if it is still open. Working notes that Claude writes before a step are
    shown in a quieter style than the answer.
    Plain: reloading never loses your place, and a chat that needs you says so from anywhere in the app.

A18. **Approvals follow the person's own Claude Code setting (Ian, 2026-11-11: "the app is asking me to
    Allow every grep").** Cause, confirmed: Ian's terminal runs in Claude Code's auto mode
    (`permissions.defaultMode: "auto"` in `~/.claude/settings.json`) while the app forced `default`. The
    brain denies reading secrets files, so in `default` mode a recursive `grep` over `clients` has to ask.
    Fix: for each new chat the server reads `permissions.defaultMode` from `~/.claude/settings.json`, then
    the brain's `.claude/settings.json`, then its `.claude/settings.local.json` (later wins). `auto` and
    `acceptEdits` are passed through; anything else, missing or unreadable, including
    `bypassPermissions`, `dontAsk` and `plan`, becomes `default`. Verified by a spike in the fake brain: in
    `auto` the SDK made no approval calls for a search, a file save and a web fetch, and it documents that
    it prompts through `canUseTool` when its safety check cannot decide. This replaces "pure `default`
    mode" in decision 5 and overseer decision (c). Settings shows the mode in plain words.
    Plain: the app asks you exactly as often as your terminal does, and can never be set to stop asking
    altogether.
    Narrowed at the overseer's sign-off: `auto` counts only when it comes from the person's own
    `~/.claude/settings.json`. In either of the brain's settings files it is read as `default`, because
    the brain's settings file syncs to the whole team. `acceptEdits` may come from any of the three.
    Plain: no shared brain file can switch off approval cards for everyone.
